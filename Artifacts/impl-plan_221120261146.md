# Stage 4 — Implementation Planning (Gate 4)

## Approved direction and scope

- Latest approved preference: black/dark base with orange accents only; do not introduce another brand accent.
- Use CSS tokens; exact hex values and orange-semantic mapping remain deferred.
- Preserve existing calculator behavior. Scope is `src/App.css` (expected), `src/index.css` (conditional), and `src/App.jsx` (conditional/minimal, only for necessary semantics or accessibility).
- Do not modify `src/main.jsx`, package manifests/lockfiles, backend/API, or calculator behavior. No dependencies are planned.
- Keep the existing `eval` risk out of this presentation work and carry it to Security Remediation.

## Suggested commit breakdown

1. **Theme and interaction styling:** Commit T-2 (only if needed) and T-3 together as a cohesive CSS change.
2. **Accessibility markup, if needed:** Commit T-4 separately, only when a specific necessary JSX change has been identified; otherwise no JSX commit.
3. Keep verification evidence in the applicable later-stage artifact; this plan creates no source-code changes or implementation commits.

## Verification approach

- **Commands:** `npm run build` and `npm run lint` (the existing package scripts); no test script is defined, and no dependency or test framework is to be added for this scope.
- **Manual visual checks:** Inspect the existing calculator at its current desktop composition and narrow/responsive widths. Confirm a coherent black/dark and orange presentation, legible text, and that selected token values are recorded as implementation choices rather than approved fixed hex values or semantics.
- **Accessibility checks:** Keyboard-tab through the existing controls in logical DOM order; confirm visible `:focus-visible`, hover and active feedback, native button operation, sufficient text/background contrast against WCAG AA, and that operator meaning is not conveyed by color alone.
- **Behavior/regression checks:** Exercise clear, digits, decimal, operators, and equals using representative valid inputs; compare with the baseline and ensure display, labels, and existing behavior remain unchanged.
- **Scope checks:** Review the diff to confirm only the approved styling files and any strictly necessary minimal JSX are touched; no `src/main.jsx`, manifests/lockfiles, backend/API, dependencies, or behavior redesign.
- **Security handoff:** Do not change `eval` in this stage. Record it for assessment and remediation in Security Remediation as required by design decision D6.

## Blockers and assumptions

- **No blocking issue for planning.** Exact color hex values and orange-to-element semantics are deferred. Implementation may use documented candidate token values for a coherent theme; final visual review remains the acceptance mechanism, and any contractual palette specification requires approval before it is treated as fixed.
- `src/index.css` and `src/App.jsx` are conditional; do not edit them unless T-1/T-3 establishes the stated need.
- Existing UI structure, buttons, responsive behavior, and calculator logic are to be preserved. The plan does not assume new functionality or new tests.
- Existing `eval` is a known security concern intentionally excluded from presentation scope and handed off to Security Remediation.
