# Design Review — SCRUM-6: Enhance Calculator application (Button Color Coding)

**Stage 3 — Design Review (Gate 3)**

Reviewed artifact: `Artifacts/architecture_231120261258.md` (CSS-only, 4-category button color coding).
Acceptance criteria checked against: `Artifacts/requirements_231120261250.md` → Acceptance Criteria section (AC-1..AC-7) only.
`src/App.jsx` was briefly inspected (read-only) to verify the architecture's open class-name assumption; no source file was edited.

## 1. Summary
The architecture is a low-risk, additive, CSS-only change (new custom-property tokens + 4 category selectors + a shared `:focus-visible` rule in `src/App.css`), with no changes to React state, handlers, or the `eval()`-based `calculate()` logic. The proposed color palette (numbers `#3A3A3A`/`#F5F5F5`, operators `#D9822B`/`#1A1A1A`, clear `#C0392B`/`#FFFFFF`, equals `#6C4BD1`/`#FFFFFF`, shared white `:focus-visible` outline) was already approved by the user in Stage 2. I independently recomputed the WCAG relative-luminance contrast ratio for all four pairs — all four match the architecture's stated figures (10.4:1, 5.9:1, 5.4:1, 5.9:1) and clear the 4.5:1 AA bar. The one open item flagged in the architecture (whether `src/App.jsx` number/operator buttons already have a distinguishing class) was resolved by direct inspection: **they do not** — this materially changes the `src/App.jsx` work from "conditional" to "required," and the architecture has been updated accordingly (see Decisions). Overall: approved to proceed to Implementation Planning once the action items below are carried into the plan.

## 2. Strengths
1. Correctly scoped as CSS-only with explicit "no logic change" boundary — matches FR/NFR intent and keeps blast radius to 2 files.
2. Contrast math is accurate, not estimated — independently re-verified all four background/text pairs against the WCAG formula; all exceed 4.5:1 with margin.
3. Reuses the existing design-token pattern (`--accent` in `src/index.css`) rather than inventing a new styling mechanism — no new dependency.
4. Explicitly preserves existing `.zero`/`.clear`/`.equals` grid-span rules and documents that category color classes can co-exist on the same element.
5. Addresses a11y beyond raw contrast: adds `:focus-visible`, keeps hover feedback, and correctly notes that label text (not color alone) distinguishes buttons within a category.
6. Explicitly defers `eval()`/CWE-95 (CWE already flagged in requirements) to Security Remediation rather than conflating scope.
7. Honestly flagged its own open assumption (App.jsx class names) instead of silently guessing — made this review's verification straightforward.

Architecture Sections 2, 9, 10 updated to state the exact required className additions (no longer conditional). |
| R2 | AC-1 explicitly includes the decimal (`.`) button under "number buttons," but the original architecture text only said "add a className to number and/or operator buttons," without naming the decimal or zero buttons specifically — risk of the decimal button being missed during implementation since it sits outside the digit block visually. | Medium | Architecture updated to explicitly list `className="number"` on the decimal button and `className="zero number"` on the `0` button (combining with the existing `.zero` grid-span class). |

A missed/misspelled CSS custom property would silently fall back to inherited color with no test to catch it. | Low | Keep as manual check (acceptable for a CSS-only, 2-file change) but require it explicitly as a named verification step in Implementation Planning / Verify stage (see Action Items), checked against AC-1–AC-6. |
| R4 | The shared `:focus-visible` outline (`2px solid #FFFFFF`, `outline-offset: 2px`) is correct in isolation, but with buttons laid out in a tight CSS grid, the 2px offset could visually clip against an adjacent button rather than showing cleanly against the `#222` panel. | Low | No architecture change required (design intent is sound). ## 5. Decisions
1. **Palette is final.** Restating the user's Stage 2 approval (most recent instruction on this point, per recency rule): numbers `#3A3A3A`/`#F5F5F5`, operators `#D9822B`/`#1A1A1A`, clear `#C0392B`/`#FFFFFF`, equals `#6C4BD1`/`#FFFFFF`, shared white `:focus-visible` outline — no further changes requested or made to the hex values.
2. **App.jsx assumption resolved as TRUE.** Confirmed via direct inspection that number/operator buttons have no existing distinguishing class. `architecture_231120261258.md` Sections 2, 5 (header), 9, 10, and the closing stage-anchor block were updated to: (a) change this work item from "conditional" to "required," (b) list the exact className additions (`number` on digits 1-9 and decimal; `zero number` combined on the `0` button; `operator` on `÷ × − +`), and (c) mark Section 5's palette as APPROVED rather than pending.
3. **Decimal and zero button className handling decided:** `className="number"` added to the decimal (`.`) button; the `0` button's existing `className="zero"` becomes `className="zero number"` (both classes co-exist, consistent with the architecture's stated grid-span-compatibility design).
4. **No architecture change needed for R3 (test coverage) or R4 (focus-outline clipping) or R5 (color-blind hue proximity)** — these are carried forward as Implementation Planning / Verify action items rather than architecture revisions, since the existing design is sound and the gaps are process-level, not structural.
5. Design Review approves `architecture_231120261258.md` (as revised in this stage) to proceed to Implementation Planning.
