# Stage 2 — Architecture (Gate 2)

## Overview

Preserve the existing React/Vite client-side calculator behavior while applying an approved black-and-orange visual theme. The architecture will keep the current `App` component and local React state as the implementation boundary; styling will be updated primarily in `src/App.css`, with shared base/theme tokens in `src/index.css` only if needed for consistency.

This design addresses **FR-1** and **AC-1/AC-2** by making the existing interface demonstrate a coherent black-and-orange palette. Exact color values and semantic mappings are not yet specified; the proposal below labels these choices as recommendations.

## Component List and Responsibilities

| Component/file | Responsibility | Architecture decision |
|---|---|---|
| `src/App.jsx` | Owns display/operator/operand state, handles button actions, and renders the calculator UI. | Preserve existing state and behavior; add no new component or dependency unless implementation discovers a necessary structural need. |
| `src/App.css` | Defines calculator layout, button grid, display, and component-level visual states. | Define black and orange CSS custom properties/tokens and apply them to the existing elements; include hover, active, and focus-visible states. |
| `src/index.css` | Defines global page, root, typography, and shared CSS variables. | Coordinate global black/orange tokens and remove or stop using conflicting template palette rules only within the style scope. |
| `src/main.jsx` | Mounts the React application. | No functional or architectural change expected. |
| `index.html` | Provides the application entry document and page metadata. | No change expected unless an accessibility/documentation refinement is approved later. |

## Data Flow

```text
User input (number/operator/decimal/C/=)
  -> existing App event handlers
  -> React state update (display, firstNumber, operator, waitingForSecondNumber)
  -> existing calculate/clear/decimal logic
  -> App re-render
  -> App.css applies black/orange theme and visual states
```

There is no backend, persistent storage, API, or external data dependency. The proposed palette affects presentation only; it does not alter calculation state or event flow.

## Technology Choices

1. Continue with React function components and hooks; no class components or state libraries.
2. Continue with JavaScript, CSS, Vite, and the existing package dependencies.
3. Use native CSS custom properties/tokens instead of inline styles or a new styling library.
4. Use semantic HTML button elements already present in `App.jsx`; add accessible names and state information only where needed.
5. Make no package or lockfile changes.

## Error Handling Approach

1. Preserve the existing no-op behavior for `=` when an operator or first operand is absent.
2. Preserve existing number, decimal, clear, operator, and equals behavior.
3. Theme-related work introduces no asynchronous operations or network error paths.
4. **Recommendation:** divide-by-zero, overflow, and invalid-result presentation should remain behaviorally unchanged unless a later requirement explicitly changes them. The implementation should not introduce browser alerts or console-only behavior as a visual workaround.
5. Invalid or unavailable CSS must not affect keyboard operation or state updates; the existing functional markup remains authoritative.

## Security Considerations

1. No secrets, credentials, authentication, authorization, network calls, or personal data are introduced.
2. React text rendering and existing local-only state reduce UI injection risk.
3. The current `calculate` implementation is based on `eval` of the operator expression. Architecture should treat this as an existing code-risk item, not as part of the visual enhancement: preserve externally observable behavior, but a later implementation/security stage may replace it with explicit arithmetic to remove dynamic evaluation.
4. No third-party assets or runtime dependencies are proposed.
5. New CSS must not use URLs, scripts, data exfiltration channels, or untrusted values.

## Assumptions and Constraints

1. **Approved preference:** the UI shall use a black-and-orange color combination.
2. **Recommendation—not a fixed specification:** orange may identify primary actions or operators, while black/dark surfaces form the base and display. This semantic mapping is not specified by **FR-1**, **AC-2**, or **NFR-1** and requires human approval before implementation if the mapping is considered contractual.
3. Exact hex values, target contrast ratios, color semantics, and visual reference are not defined by the approved requirements artifact. No exact values are invented here.
4. Existing calculator behavior is preserved; this stage adds presentation changes only.
5. Accessibility is a required implementation quality under the repository instructions, even though the requirements artifact currently defers formal accessibility criteria in **NFR-1**.
6. The active branch for this workflow is `ghcp-capstone-after-review`.

## Review Decisions and Coverage

1. **Gate 3 decision — Palette:** Preserve the approved black-and-orange combination. Neutral text may be used for legibility, but the theme shall not introduce an additional brand accent palette.
2. **Gate 3 decision — Scope:** The review is presentation-only. **App.jsx**, calculation state/handlers, package dependencies, and `main.jsx` remain unchanged unless a later stage identifies an accessibility necessity.
3. **Gate 3 decision — Exact values:** Hex values and the orange-semantic mapping remain deferred; implementation may choose only from approved requirement context and must document the selected tokens.
4. **Gate 3 decision — Interaction quality:** Hover, active, and keyboard focus states are required for interactive buttons, with a visible focus indicator and no color-only meaning.
5. **Gate 3 decision — Coverage:** AC-1 is covered by preserving the existing application and applying a theme to it; AC-2 is covered by the presence of a coherent black-and-orange presentation. Final visual review remains the acceptance mechanism because exact colors and semantics are deferred.
6. **Gate 3 decision — Existing eval risk:** Do not change calculation implementation in this presentation stage. Dynamic evaluation is a separate security concern to be handled in Security Remediation or a later scoped stage.

## UI Structure and Styling

1. Retain the existing `.calculator` container, `.display` region, `.buttons` grid, clear/equals/zero button spans, and all button labels.
2. Recommendation: use a dark/black calculator surface and display, orange accents for action emphasis, and neutral text suitable for measured contrast.
3. Use CSS variables for:
   - base/background colors
   - surface colors
   - orange accent colors
   - text/icon colors
   - focus indicator color
   - interaction state modifiers
4. Define `:hover`, `:active`, and `:focus-visible` states for every interactive button.
5. Avoid `opacity` alone as an interaction state because it can reduce text contrast; use explicit tokenized state changes.
6. Preserve the 320 px desktop composition and responsive behavior already implied by the existing calculator layout; no new breakpoint requirement is specified.

## Accessibility Considerations

1. Keep native `<button>` elements for keyboard operability and semantic role.
2. Add visible `:focus-visible` outlines that are not removed or hidden.
3. Maintain text/background contrast; final values must be checked against WCAG AA after implementation.
4. Do not encode operator meaning by color alone; retain visible symbols and labels.
5. Keep display output perceivable and use an accessible text representation for the existing visible display if future review requires it.
6. Preserve logical visual and DOM focus order. The grid layout must not reorder keyboard navigation separately from the existing markup.

## Gate 2 Result

`PASS` — the architecture identifies impacted components/files and includes styling/structure plus accessibility considerations.
