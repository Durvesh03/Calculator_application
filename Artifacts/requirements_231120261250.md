## Problem Statement
Story text: "Enhance the existing calculator application with proper color coding"

Current implementation, inspected in this repo:
- `src/App.jsx` renders calculator buttons in four categories: number buttons (`0`-`9`, zero, decimal `.`), operator buttons (`÷ × − +`), a clear button (`C`), and an equals button (`=`).
- `src/App.css` defines only generic styling shared by all buttons — `height`, `border`, `border-radius`, `font-size`, `cursor`, and a shared `button:hover { opacity: 0.8 }` rule. The `.clear`, `.equals`, `.zero` classes only control **grid layout** (`grid-column`/`grid-row` span) — none of them set a distinct background/text color.
- Result: all four button categories currently look visually identical (no color differentiation), making it hard for users to quickly distinguish numbers from operators, clear, and equals, increasing mis-click risk.

This story asks for color coding to be added so the four button categories are visually distinguishable.

## In Scope
- Updating `src/App.css` (and, only if a styling hook is needed, adding class names in `src/App.jsx`) to apply distinct color treatments to:
  - Number buttons (`0`-`9`, decimal `.`)
  - Operator buttons (`÷ × − +`)
  - Clear button (`C`)
  - Equals button (`=`)
- Ensuring sufficient text/background contrast for the new colors against the existing dark `.calculator` panel (`#222`) and `.display` (`#111`) backgrounds.
- Preserving existing hover feedback (`button:hover { opacity: 0.8 }` or equivalent) across all recolored buttons.
- Preserving existing grid layout/span rules (`.clear`, `.equals`, `.zero`) — this story changes color/visual styling only, not layout or functional logic.

## Out of Scope
- Any change to calculator computation logic in `src/App.jsx` (`inputNumber`, `inputOperator`, `calculate`, `handleEquals`, `clearCalculator`, `handleDecimal`). Note: `calculate()` currently uses `eval()` (flagged in-code as CWE-95); this is a pre-existing issue, not part of this color-coding story, and is deferred to the Security Remediation stage if raised.
- Introducing a user-facing light/dark theme toggle, or any `prefers-color-scheme` light/dark adaptation, for the calculator component. **Confirmed by user**: the calculator stays within its current single hard-coded dark theme (`#222`/`#111`); `src/index.css`'s existing `prefers-color-scheme: dark` media query (which only affects surrounding page chrome, not `.calculator`) is not extended to the calculator.
- New calculator features (memory, history, keyboard input, percentage, scientific functions) not requested in the story.
- Non-browser platforms / native wrappers.

## Functional Requirements
- **FR-1**: Number buttons (`0`-`9`, decimal `.`, zero) SHALL share one consistent color treatment, visually distinct from operator, clear, and equals buttons.
- **FR-2**: Operator buttons (`÷`, `×`, `−`, `+`) SHALL share one consistent color treatment, visually distinct from number, clear, and equals buttons.
- **FR-3**: The Clear button (`C`) SHALL use a color treatment that visually signals a destructive/reset action, distinct from the other three categories.
- **FR-4**: The Equals button (`=`) SHALL use a color treatment that visually signals a primary/confirm action, distinct from the other three categories.
- **FR-5**: All color changes SHALL be implemented via CSS (`src/App.css`), without altering button markup/handlers in `src/App.jsx`, except for adding class names strictly needed as styling hooks.
- **FR-6**: The existing hover feedback currently defined as `button:hover { opacity: 0.8 }` SHALL remain present (or be equivalently preserved) for every button category after recoloring.

## Non-Functional Requirements
- **NFR-1 (Accessibility/Contrast)**: Text-to-background contrast for every button category SHALL meet WCAG 2.1 AA minimum (4.5:1 for normal text) against its own background and remain legible against the surrounding `.calculator` panel background (`#222`).
- **NFR-2 (Consistency/Maintainability)**: New colors SHALL be defined as CSS custom properties/variables (consistent with the token pattern already used in `src/index.css`, e.g. `--accent`) rather than one-off hard-coded hex values repeated across rules.
- **NFR-3 (No functional regression)**: The change SHALL NOT alter calculator arithmetic behavior, grid layout/spans, or responsiveness — visual/color styling only.
- **NFR-4 (Keyboard focus visibility)**: Any new button color treatment SHALL NOT remove or obscure a visible `:focus-visible` indicator for keyboard users; focus outlines must remain legible against each new button color.
- **NFR-5 (Browser support / no new deps)**: Color coding SHALL render consistently in evergreen browsers (Chrome, Edge, Firefox, Safari) using standard CSS, with no new runtime dependencies added.

## Acceptance Criteria
- **AC-1**: Given the calculator is rendered, number buttons (`0`-`9`, decimal) are styled with one color scheme that is visibly different from operator, clear, and equals buttons.
- **AC-2**: Given the calculator is rendered, the four operator buttons (`÷ × − +`) share one distinct color scheme, visibly different from number, clear, and equals buttons.
- **AC-3**: Given the calculator is rendered, the Clear (`C`) button has a distinct color visibly different from the other three categories.
- **AC-4**: Given the calculator is rendered, the Equals (`=`) button has a distinct color visibly different from the other three categories.
- **AC-5**: Given a user hovers over any button, the existing hover feedback still occurs, regardless of button category.
- **AC-6**: Given the recolored buttons, the button label text meets at least a 4.5:1 contrast ratio against its own background color (WCAG AA, normal text).
- **AC-7**: Given the calculator after the change, performing a sample calculation (e.g., `2 + 3 =`) still produces the correct result (`5`) — confirming no functional regression from the styling change.

## Open Questions — Resolved
- **Q1 (Resolved)**: Exact color palette per category (numbers / operators / clear / equals) — **user answer: "Any color combination is fine."** The exact palette is deferred to the Architecture stage to propose for approval; this requirements document deliberately mandates no specific hex values (see FR-1..FR-4, NFR-2).
- **Q2 (Resolved)**: Whether the calculator's color coding should also adapt to the existing `prefers-color-scheme` light/dark support in `src/index.css` — **user answer: "should be dark."** Confirmed: the calculator stays within its current single hard-coded dark theme (`#222`/`#111`); no light/dark toggle or `prefers-color-scheme` adaptation is added for `.calculator` (see Out of Scope).

## Confirmed Scope Decisions (Architecture stage starting point)
- Exact palette per button category (numbers / operators / clear / equals) is not mandated here — the Architecture stage will propose specific colors/tokens (e.g., numbers = neutral dark gray, operators = amber/orange, clear = red, equals = the existing `--accent` purple token from `src/index.css`, as one possible starting proposal) for user approval before implementation.
- Scope is confirmed limited to the calculator's current single dark theme (`#222`/`#111`); no light/dark adaptation is in scope for this story.
