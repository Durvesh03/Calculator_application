# Stage 3 — Design Review (Gate 3)

## Summary

The architecture is **conditionally approved** after revision. It preserves the existing React/Vite calculator, limits changes to the presentation scope, uses native controls and CSS tokens, and adds the approved black-and-orange direction. It does not alter package dependencies or calculation behavior.

Coverage:
- **AC-1:** Partial/adequate architectural coverage—an existing calculator enhancement is specified, but visual verification criteria remain qualitative.
- **AC-2:** Adequate for the current approved preference—black and orange are explicitly required, while exact palette and semantic mapping remain deferred by the requirements.

## Strengths

- Clear component and file impact boundaries.
- Existing state/event flow is preserved rather than redesigned.
- Native button elements and explicit focus-visible requirements retain keyboard operability.
- CSS custom properties provide a maintainable theme mechanism.
- No backend, network, storage, secrets, third-party assets, or dependency changes are proposed.
- Existing dynamic evaluation is correctly identified as out of scope for the visual enhancement.

## Risks/Gaps (severity + mitigation)

| Severity | Risk/Gap | Mitigation |
|---|---|---|
| High | Exact black/orange hex values and target contrast are not defined, so implementation cannot prove WCAG AA or AC-2 objectively. | Defer exact values and visual semantics under the existing requirements; implementation must use a documented token set and provide contrast evidence during verification. Pending approval: approve exact palette values and operator semantics before implementation if contractual acceptance is required. |
| Medium | The `src/index.css` role is conditional and could conflict with template palette rules or token ownership. | `App.css` is the primary implementation scope; `index.css` may change only shared base/page tokens and must remove or stop conflicting template palette rules. |
| Medium | `eval` remains in the calculation path and is explicitly described as vulnerable. | Keep it out of presentation scope for this stage; Security Remediation must assess and remediate it if in workflow scope. |
| Medium | AC-2 has no measurable visual acceptance criteria beyond “proper color coding.” | Use a screenshot/manual visual check after implementation: black/dark surfaces plus orange accents are visibly coherent and no unrelated accent color is introduced. |
| Low | Hover behavior currently uses `opacity`, which can reduce contrast and conflict with explicit interaction-state guidance. | Architecture requires explicit tokenized hover/active states instead of opacity as the sole change. |
| Low | The display lacks a specified accessible text representation or live region behavior. | Preserve existing markup; implementation may add minimal accessible markup only if needed and must not reorder DOM/focus navigation. |

## Decisions

1. **D1 — Black/orange only:** Use a dark/black base and orange accents; no additional brand accent palette.
2. **D2 — Presentation-only scope:** Preserve `App.jsx` behavior and state unless later accessibility needs minimally justify markup changes.
3. **D3 — CSS tokenization:** Use CSS custom properties for surface, accent, text, focus, and interaction states.
4. **D4 — Interaction states:** Implement hover, active, and visible `:focus-visible` states for every button; do not rely on color alone.
5. **D5 — Deferred visual specification:** Exact hex values and orange-semantic mapping remain open rather than invented.
6. **D6 — Evaluation security:** Do not remediate `eval` during this design stage; carry the risk explicitly to the Security Remediation stage.

## Action items

1. Before implementation, the approver must decide whether exact hex values and operator/color semantics are contractual.
2. If approved, update the architecture during the implementation planning handoff or a later stage with exact palette tokens and contrast targets.
3. Implementation Planning must verify black/orange visual coverage, interaction states, keyboard focus, and preservation of calculator behavior.
4. Security Remediation must assess the existing `eval` implementation if it is in scope.
