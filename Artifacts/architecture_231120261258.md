# Architecture — SCRUM-6: Enhance Calculator application (Button Color Coding)

## Status
APPROVED — color palette/tokens in Section 5 confirmed by user. App.jsx class-name assumption (Section 10) confirmed via Design Review inspection of `src/App.jsx` (Gate 3); see `Artifacts/design-review_231120260100.md`.

## 1. Overview
This is a CSS-only visual enhancement to the existing calculator. Four button categories — numbers, operators, clear, equals — currently render with identical styling (`src/App.css` only sets shared `height`/`border`/`border-radius`/`font-size`/`cursor`/hover). The architecture introduces a small set of CSS custom properties ("design tokens") scoped to the calculator, one background/text pair per category, applied via category-level CSS class selectors. No component structure, state, or computation logic changes. This satisfies FR-1..FR-6 and NFR-1..NFR-5 with a single, low-risk, additive change confined almost entirely to `src/App.css`.

## 2. Component List & Responsibilities
| Component/File | Responsibility | Change type |
|---|---|---|
| `src/App.css` | Defines calculator visual styling; will gain a token block (CSS custom properties) + 4 new category rule-sets (`.number`, `.operator`, `.clear`, `.equals`) for background/text color, plus a shared `:focus-visible` rule. | Primary change |
| `src/App.jsx` | Renders button elements and owns `inputNumber`, `inputOperator`, `calculate`, `handleEquals`, `clearCalculator`, `handleDecimal`. **No logic changes.** **CONFIRMED (Design Review, Gate 3):** digit buttons (`1`-`9`, `.` decimal) and all four operator buttons (`÷ × − +`) currently have **no** className at all; only `C`→`.clear`, `=`→`.equals`, `0`→`.zero` exist. Required additions: `className="number"` on `1`-`9` and `.`; `className="zero number"` on `0`; `className="operator"` on `÷ × − +`. | Additive only (class name attribute literal strings; no handler/logic/JSX-structure edits) |
| `.calculator` panel (existing, in `App.css`) | Dark container background (`#222`) that all buttons sit on. | No change — contrast reference only |
| `.display` (existing, in `App.css`) | Dark readout background (`#111`). | No change — contrast reference only |

## 3. Data Flow (Text Diagram)
No data/state flow changes. Visual-only flow:
```
User click/keyboard focus on a <button>
        │
        ▼
Existing React event handler (unchanged: inputNumber/inputOperator/clearCalculator/handleEquals)
        │
        ▼
State update → re-render (unchanged)
        │
        ▼
Button's existing CSS class (.number | .operator | .clear | .equals)
        │
        ▼
NEW: category rule resolves --btn-*-bg / --btn-*-text custom properties
        │
        ▼
Browser paints button background/text color; :hover and :focus-visible rules layer on top unchanged in trigger logic, new in color-safe styling
```
Arithmetic state (`display`, `previousValue`, `operator`, etc.) is untouched — confirms NFR-3 / AC-7.

## 4. Technology Choices
- **Plain CSS custom properties** (`--btn-number-bg`, etc.), defined once (e.g., in a `:root` or `.calculator` scope in `src/App.css`), consumed by category selectors — matches the existing token pattern (`--accent`) referenced in `src/index.css`, satisfying NFR-2.
- **No new dependencies** (no CSS-in-JS library, no Sass/PostCSS plugin) — satisfies NFR-5 and the "no new dependencies" guardrail.
- **Class-based selectors** (`.number`, `.operator`, `.clear`, `.equals`) rather than inline styles, so colors stay centralized and overridable, and existing `.zero`/`.clear`/`.equals` grid-span rules are left fully intact (selectors can co-exist on the same element).
- **Single hard-coded dark theme only** — no `prefers-color-scheme` media query added for `.calculator` (per confirmed scope decision; `src/index.css`'s existing light/dark query for page chrome is left untouched).

## 5. Color Palette / Tokens (APPROVED)
Addresses FR-1, FR-2, FR-3, FR-4, NFR-1, NFR-2, AC-1–AC-4, AC-6. All ratios below are computed against the stated background using the WCAG relative-luminance formula (verified, not estimated):

| Category | Token names | Background | Text | Contrast (text vs own bg) | Semantic rationale |
|---|---|---|---|---|---|
| Numbers | `--btn-number-bg`, `--btn-number-text` | `#3A3A3A` | `#F5F5F5` | **10.4:1** | Neutral dark gray, slightly lighter than the `#222` panel — reads as the "default/base" key |
| Operators | `--btn-operator-bg`, `--btn-operator-text` | `#D9822B` (amber) | `#1A1A1A` | **5.9:1** | Warm amber signals "action/transform", distinct hue from numbers |
| Clear (C) | `--btn-clear-bg`, `--btn-clear-text` | `#C0392B` (red) | `#FFFFFF` | **5.4:1** | Red = conventional destructive/reset signal (FR-3) |
| Equals (=) | `--btn-equals-bg`, `--btn-equals-text` | `#6C4BD1` (purple) | `#FFFFFF` | **5.9:1** | Purple = conventional primary/confirm action (FR-4); distinct from the other three |

All four pairs clear the WCAG AA 4.5:1 minimum for normal text (NFR-1, AC-6) with comfortable margin, and all four backgrounds are visually distinguishable from each other and from the `#222` panel / `#111` display.

Shared focus style (new, addresses NFR-4):
```css
:focus-visible {
  outline: 2px solid #FFFFFF;
  outline-offset: 2px;
}
```
A 2px solid white outline with offset remains legible against all four backgrounds above (each has either enough contrast against white, or the offset puts the outline against the `#222` panel instead of the button face).

Existing hover rule `button:hover { opacity: 0.8 }` is preserved unchanged and layers on top of the new backgrounds (addresses FR-6, AC-5) — opacity reduction keeps each category's hue identifiable while still giving feedback.

**APPROVED by user (confirmed in Stage 2, prior to Design Review) — palette and focus-outline treatment above are final; contrast figures independently re-verified during Design Review (Gate 3).**

## 6. Error Handling Approach
This change has no runtime logic, so there is no new error path to handle. Risk is purely visual regression:
- If a token is undefined/misspelled, the browser silently falls back to `initial`/inherited color — mitigated by defining all tokens once in a single visible block at the top of `src/App.css` and reviewing visually (and via the existing AC-7 manual calculation check) before merge.
- No change to `calculate()`/`eval()` error handling — explicitly out of scope (deferred to Security Remediation per requirements.md).

## 7. Security Considerations
- Pure CSS/presentational change — no new attack surface, no user input processed, no new dependency, no network/storage access.
- Confirms the `eval()` usage in `calculate()` (CWE-95, flagged in requirements.md) is **not** touched by this change and remains explicitly deferred to the Security Remediation stage, per Out of Scope.
- No secrets, tokens, or credentials are involved in a CSS/color-token change.

## 8. Accessibility (a11y) Considerations
- **Contrast**: all four category text/background pairs verified ≥ 4.5:1 (see table above) — satisfies NFR-1/AC-6.
- **Focus visibility**: explicit `:focus-visible` outline added (white, 2px, offset) so keyboard users retain a visible indicator on every recolored button — satisfies NFR-4.
- **Hover preserved**: `button:hover { opacity: 0.8 }` kept as-is — satisfies FR-6/AC-5.
- **No color-only ambiguity within a category**: each button still shows its label text (`C`, `=`, digits, operator glyphs) — color reinforces but does not solely convey category, avoiding a color-only-meaning a11y pitfall.

## 9. Impacted Files (Gate 2 requirement)
1. `src/App.css` — primary and expected sole change: add token declarations + `.number`/`.operator`/`.clear`/`.equals` color rules + `:focus-visible` rule. Existing `.clear`/`.equals`/`.zero` grid-span rules untouched.
2. `src/App.jsx` — **additive only (confirmed required, Gate 3)**: add `className="number"` to the nine digit buttons (`1`-`9`) and the decimal (`.`) button; change `className="zero"` to `className="zero number"` on the `0` button; add `className="operator"` to all four operator buttons (`÷ × − +`). No change to any handler (`inputNumber`, `inputOperator`, `calculate`, `handleEquals`, `clearCalculator`, `handleDecimal`), onClick wiring, or JSX structure otherwise.

No other files are in scope.

## 10. Assumptions / Constraints
- **Confirmed (Design Review, Gate 3)**: number and operator buttons lack any distinguishing CSS class — only `.clear`, `.equals`, `.zero` exist in current `src/App.jsx`. Adding `.number`/`.operator` classNames (see Sections 2 and 9) is a styling hook only, explicitly permitted by FR-5, and is now a required (not conditional) implementation step.
- Constraint: no new npm dependency, no CSS preprocessor, no `prefers-color-scheme` logic added for `.calculator` (confirmed single dark theme only).
- Constraint: `.zero`'s existing grid-span rule and the `.clear`/`.equals` grid-span rules must remain combinable with the new color classes on the same element (e.g., a button can be both `.zero` and `.number`).
- Assumption: the exact hex values proposed in Section 5 are a starting recommendation, not final — user approval required before Design Review proceeds on this basis.
- Constraint: this stage does not modify any source file — only this architecture artifact was written.
